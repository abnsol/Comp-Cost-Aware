Implemented behavior
Wrap native PLN.Derive with a guard at each entry, including the initial entry.
Check elapsed engine CPU, scan committed beliefs for the exact query and the
declared strength/confidence criterion, then recheck elapsed CPU. If a qualifying
record is found in time, stop. Otherwise continue the original native loop unless
its deadline, step cap or empty-task termination applies. Never change candidate
priority, input order, evidence guards, rules, queue caps or queue updates.
Timing mode silences only native SELECTED console printing. Audit mode retains
all original state/proof/selection records for parity checks.
The adapter receives KB, query, acceptance thresholds, CPU budget and original
native caps. It receives NO saved proof, expected queues or known first-goal step.
It is an online stopping adapter around PLN, not the original PLN.Query API and
not a cost-aware selector. It returns the first numerically acceptable record in
belief order. Full proof replay remains offline and uses pinned PLN formulas.

CPU accounting and deadline semantics
The budget starts after ground inputs/callable are prepared and ends after the
native call returns, with recursion unwind and adapter state retrieval included.
Charged CPU includes native selection/inference/queue work, guard setup, goal
scans, clocks and bookkeeping. Loaded-engine user+system CPU is read through
embedded Python process_time_ns. Startup/loading, parent orchestration, final
harness status formatting/serialization and offline proof replay are excluded.
Parent invocation CPU and wall time are saved separately. Do not add them to
engine CPU as though they measured an online answer event. No costs are subtracted.
Success requires a detected, subsequently verified answer and final native-call
CPU <= budget. An answer that exists only in an over-budget state is a miss.
Forty missed runs contained a goal record in the final native state; none was
rescued using offline checkpoint/proof knowledge.

Cooperative overshoot
Expansions are atomic here; clock checks cannot interrupt a rule scan or queue
update already running. A deadline thus limits credited answer latency, not a
strictly preempted CPU allocation. Zero-budget validation stopped before any
expansion. Positive-budget trials can exceed the allotted amount before the
next boundary. This is a material limitation if a future application needs a
hard resource cap or comparisons that guarantee identical actual CPU spent.
Maximum observed overshoot: 1.890501 ms.
Median overshoot among the260 misses: 0.176910 ms.
Raw actual CPU and overshoot are retained for every call, not clipped to budget.

Online observation cost diagnostic
The sum of guard observation windows is INCLUDED in total CPU. It covers the
query scan, some checks and clock boundaries; it excludes some state updates/
dispatch/return costs. It is not the exact causal overhead relative to an
unobserved run. Median window share among successful runs, grouped by width:
Width1: 7.97%.
Width4: 5.87%.
Width16: 3.81%.
Unlike the earlier empty-harness calibration gate, these observations are
implemented online functionality charged in full, not instrumentation costs
subtracted or excluded. No claim that they are free or negligible is made.

What this establishes, and what it does not
This baseline has valid reachable answers, real unequal local expansion costs
(step6), measured first-answer CPU (step7), and a reproducible descriptive change
in on-time completion across budgets (step8). The budget range is meaningful
for testing these small tasks, with failures/transition cells/saturated cells.
We have NOT compared cost-aware selection with the baseline. These results do
not demonstrate that predicted cost improves selection, prevents overshoot,
improves probabilistic accuracy, or generalizes to other PLN tasks or hardware.
All accepted answers still meet the same declared strength1/confidence>=0.729
proof objective. A missed deadline does not mean the query is false. Continuing
native reasoning for confidence revision remains a different objective.
