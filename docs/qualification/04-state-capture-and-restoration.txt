QUALIFICATION STEP 4: CAPTURE AND RESTORE NATIVE LOGICAL STATES
Completed. Stop for code/results review before adding CPU instrumentation.

Outcome
Captured 435 loop-entry checkpoints across the same nine qualification KBs.
Restored 47 selected checkpoints in fresh engine processes. All 47 reproduce the
exact remaining state, proof and selection events, and the exact final ordered
queues. All nine complete capture runs preserve every line of the earlier
feasibility proof/selection/output trace after removing the new state/trim prints.
This is observed parity on these cases, not proof for every possible PLN program.

Meaning of a state
The native PLN.Derive arguments are the complete explicit state of this ground
loop: ordered Tasks, ordered Beliefs, next expansion counter, maximum expansion
counter, and task/belief queue limits. Each Sentence retains its term, strength,
confidence and evidence IDs. We also save native-library and original-fixture
hashes, the state hash and the source trace-line number.
Order matters because native BestCandidate keeps the first maximum-confidence
record. The next-step counter matters because restoration must preserve the
remaining expansion allowance. We do not reset it to one or refill either queue.

The print is at entry to the seven-argument native loop, before its termination
guard. The first checkpoint is the initial KB. Every subsequent checkpoint is
after the previous expansion's complete task/belief queue updates, including any
trimming. A terminal checkpoint is captured even when no further work is done.
Restore fixtures call this same seven-argument native loop with literal saved
queues. They print its returned pair of queues for exact final-state comparison.

Logical state is not the full runtime/hardware state. Fresh processes reset
allocation history and caches. This step does not establish timing equivalence,
warm-up control or negligible restoration cost. Later profiling must control and
report those effects; restoration is not a free online selection capability.

Checkpoint selection fixed in code before execution
For each full run: initial; after one expansion; midpoint; penultimate; terminal.
Also restore the last checkpoint with both original Ready candidates pending at
equal priority, if distinct. This gives five restorations in seven cases and six
in the shuffled N4 and N16 cases: 47 total. There were 56 engine executions in
this step (9 full captures + 47 resumptions). No budgets/caps were enlarged.

Comparable Ready alternatives
Both original Ready A and Ready B are pending with confidence/priority 0.9:
- At the initial state of every case.
- After one and two expansions in shuffled N4 and shuffled N16.
These are 13 eligible checkpoints across the nine cases (not independent task
families). No CanOperate query record is present in the beliefs of those states.
Initial, midpoint or terminal restoration success alone does not make a state
eligible for comparing Ready A and Ready B: eligibility explicitly checks that
both original records are still pending. The snapshot includes both candidates.

These states support the later comparison of alternative expansions FROM THE
SAME STATE. This step has not forced either candidate, measured CPU differences,
or established which candidate reaches an answer sooner. In the natural baseline,
rule records also compete for selection and must remain in the task queue.

Implementation review order
1. src/pln_cost/states.py
   instrument_states keeps the native loop body and wraps it with an entry print;
   it retains prior proof prints and adds the queue-removal notification.
   capture_states checks initial queues, counters, cap consistency, selection's
   confidence/tie order, and membership in input or previously generated records.
   Membership checks do not independently replay every generated proof.
   ready_pair checks pending records and equal confidence.
   restore_fixture validates caller-supplied provenance/hash before rendering.
   check_restoration compares every remaining state/proof/selection/trim event,
   and final queue contents AND order, not only the eventual answer.
2. scripts/validate_states.py
   Reuses the pinned runtime and successful step-three batch. Verifies prior
   fixture/log/source hashes and runtime provenance. Writes disk snapshots, reads
   those snapshots back, then restores them in fresh processes. Keeps failures
   and continues other cases; refuses overwriting existing run IDs.
3. tests/test_states.py
   Checks queue/counter serialization, tampering, provenance, pending-candidate
   eligibility, checkpoint policy and changed continuation detection. A saved-run
   regression check validates all 47 native continuations and snapshot/log hashes.
