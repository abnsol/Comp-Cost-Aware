What the clock includes
One direct compiled call to the complete native derivation loop: native
confidence selection, rule matching/formulas, result collection, evidence guards,
deduplication, queue updates, recursion/dispatch and termination. Two Janus calls
read embedded Python process_time_ns, including engine user and system CPU.
Initial ground argument preparation precedes the clock. Source loading, engine
startup, output checks/printing, Python orchestration and offline proof replay
are outside this reasoning interval. No artificial costs/delays were added.
The generated native-library copy changes ONLY the SELECTED console print to
an empty expression. The saved quiet.diff makes that change reviewable; rules,
selector and queue operations are unchanged. Measurements describe this quiet
native baseline, not the original diagnostic printing cost.
No per-expansion observer, clock or proof recorder runs in the timed loop.
No inference warmup: each timed call is the first inference in its fresh process.
Thirty empty-call probes initialize/measure the clock bridge before inference.
The full solution-set check runs after the clock, so it cannot warm the measured
call. Parent invocation CPU and total invocation wall time are stored separately
in every run manifest. They include untimed setup/validation and cannot simply
be added to prefix CPU to claim online answer latency.

Offline checkpoint selection is not an online stopping algorithm
The saved trace identifies the exact first qualifying committed belief state.
We cap a native replay at that expansion count and verify exact prefix parity.
This is a measurement device using offline knowledge; no policy receives that
knowledge. Implementing a detector/CPU stopping check requires charging its cost.
An actual application return also requires answer extraction and any requested
online proof verification. That end-to-end behavior has not been benchmarked.

Every first goal here is generated while expanding a Certificate -> CanOperate
implication rule record. Rule records are legitimate native pending candidates;
they were never excluded to make the A/B choices look more influential.
Canonical and swapped cases expand BOTH Ready facts before the first goal.
Swapping their order leaves the first goal at expansion4; this does not prove
equal CPU or that a different cost-aware order could never help.
In N4 shuffled, the B proof succeeds at expansion6 before ReadyB is selected
at7: an implication expanded earlier already generated the B certificate.
In N16 shuffled, a B proof succeeds at5 before ReadyA is selected at23.
Thus the task is not accurately modeled as choosing exclusively between two
Ready expansions and then automatically completing that chosen route.

Interpretation and remaining limits
The local expansion-cost difference now connects to actual native work before
a valid answer on some cases. It still does not show that cost prediction
improves answer CPU or that simply swapping Ready A/B is a useful intervention.
The native search continues after this first acceptable goal. Earlier feasibility
runs returned confidence approximately0.843262 after later disjoint-proof
revision, so continued search is not automatically wasted. First-valid-proof
completion and confidence improvement are different objectives. No improved
probability accuracy against an external probabilistic reference is established.
The workload is small: first-prefix medians are roughly0.38-3.02 ms, and some
observed repeat ranges are broad. CPU-budget experiments need repeated runs;
no budget grid or significance claim is selected from these three repetitions.
An estimator/detector could consume the entire possible saving at this scale.

Next step for discussion
Design and validate an online CPU-budget boundary and first-answer observation
policy, accounting for its overhead while preserving native candidate selection.
Then test native success across a fixed range of budgets, retaining failures
and repeated-run variability. No estimator or cost-aware selector yet. After
budget testing, audit all baseline criteria and review the papers before design
or implementation of the proposed adaptation.
