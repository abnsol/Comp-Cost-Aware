STEP 8: BUDGETED NATIVE-SELECTION BASELINE
Recorded before implementation and execution, 2026-10-04.

Question: on the existing nine qualification KBs, does a finite CPU budget affect
whether a valid answer is returned by the budgeted baseline? No cost estimator or
cost-aware selection, no probability-accuracy improvement claim. Stop after this
step for user review; the final criteria audit is a later step.

Use configs/budget-protocol.json unchanged. Seven common budgets, selected from
step-seven pilot scale:0.25,0.5,1,2,4,8,16 CPU milliseconds. Ten fresh processes
per case and budget (630 measured calls). Shuffle all63 case/budget jobs within
each repetition using seed1951+repetition. Write the whole schedule before running.
Do not replace, discard or rerun unfavorable measured calls. Report exact counts
out of10, not task-generalization probabilities or claims of statistical power.

Adapter: wrap the native six-argument PLN.Derive definition with a continuation
guard at each loop entry. Native selector, rules, evidence handling, ordered
queue updates and recursive calls remain verbatim. Only native SELECTED console
printing is silenced in timing mode. Audit mode retains state/proof/selection
prints and is not a performance measurement. At every checkpoint the adapter
checks CPU, scans current committed beliefs for the exact query/declared numeric
acceptance thresholds, then checks CPU again. It has no saved answer, prefix
length, proof or expected queues as online input. A qualifying record stops the
loop. Full proof certification remains offline and uses only prior trace events
up to the actual completed checkpoint. An unsupported proof invalidates the run.

This changes native termination behavior, not native candidate selection. It is
a baseline adapter, not the original PLN.Query API. It returns the first accepted
record in belief order and makes no claim to choose the highest-confidence one.

Charge adapter state setup, all guard/goal scans, budget clocks/bookkeeping,
native selection/inference/queue updates, and unwind/return to the engine call
boundary. Ground inputs and callable are prepared before the start clock;
initialization/loading, parent Python orchestration, printed serialization and
offline certification are outside this loaded-engine CPU budget. Store parent
invocation CPU and wall duration separately; neither is a latency correction.
No inference warmup. Initialize the clock bridge before starting the budget.
Record aggregate observer-window CPU as a diagnostic INCLUDED in total CPU,
not a cost to subtract. Those windows do not capture every wrapper/clock cost.

Cooperative stopping: check at expansion boundaries; do not preempt native rule
evaluation. One expansion may overrun the budget. Report total overshoot and
completed expansions. A success requires detection and final engine-call CPU
<= budget (inclusive). Detected but returned late is a miss. A goal in a final
over-budget state is not rescued by offline verification. This is NOT a strict
hard CPU cap, and the separate60-second wall timeout remains a safety limit.

Validation before sweep: nine generous-budget audit runs must match all original
prefix states, selected records and derivations through the first valid answer;
nine quiet generous-budget runs must reach identical queues and certified goals.
Also run a zero-budget case (no expansion/success) and an absent-query case
(native exhaustion, no answer). Bind sweep to passed validation and exact adapter,
generated library, protocol, fixture-generator/runtime/source hashes.

For EVERY measured run, check returned queues against the saved native state at
the recorded expansion count, and verify any detected goal from events available
at that checkpoint. Reject malformed clocks/counters, changed queues or early
success. Keep genuine deadline misses distinct from execution/validation errors.

Do not interpret confidence as ground-truth probability accuracy. The benchmark
objective remains one valid strength1/confidence>=0.729 derivation. The completed
test can qualify a budget-sensitive baseline, not demonstrate estimator benefit.
